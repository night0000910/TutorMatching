# TutorMatching（個別指導Online）

生徒と講師の「自分に合った先生を選べない」「スケジュールが合わない」というミスマッチを解消し、オンラインで自由に講師を選んで授業を受けられる家庭教師マッチングプラットフォームです。

---

## ◯プロジェクト概要・背景

既存の教育サービス（学校・予備校・一般的な個別指導塾）では、「生徒が自分に合った先生を自由に選べない」という課題があります。
本サービスは、生徒側が自分に合う講師を検索・予約して受講でき、講師側は自身の空き時間を登録してレッスンを提供できるサービスです。

## ◯主な機能

1. **アカウント管理・認証**
   * 生徒 / 講師それぞれの役割に応じたユーザー登録・ログイン
   * プロフィール画像、氏名、自己紹介等の編集
2. **授業予約・スケジュール管理**
   * 講師：指導可能時間枠の登録・管理
   * 生徒：講師検索、指導可能枠の予約および予約一覧確認
3. **リアルタイム・ビデオチャット（※現在開発・検証中）**
   * マッチング確定後のブラウザ上でのオンラインビデオ指導（WebRTC / Django Channels）

## ◯アーキテクチャと設計思想

本システムでは、Docker Compose を用いたマルチコンテナ構成を採用し、Nginx、Django App（Web/API/WebSocket）、PostgreSQL DB の処理の流れと責務を明確に分離して設計を行っています。

### コンテナ処理の流れと役割

```
【アカウント登録〜授業予約】

[ Client (Browser) ]
   │
   ├─► ① HTTP Request (画面表示 / 静的ファイル) ──────┐
   ├─► ② REST API Request (データ取得・更新) ────────┼──► [ Container: Nginx ]
   └─► ③ WebSocket (WebRTC Signalling) ──────────────┘           │
                                                                 ▼
                                                       [ Container: App ]
                                                       ├─ Django (認証・画面表示)
                                                       ├─ DRF (データ取得・集計 API)
                                                       └─ Signalling (WebSocket)
                                                                 │
                                                                 ▼
                                                       [ Container: DB ]
                                                       └─ PostgreSQL (CRUD)

【授業実施中】

[ Client (Student) ] <==== ④ WebRTC (Peer-to-Peer Video/Audio) ====> [ Client (Tutor) ]
```

* **Nginx（リバースプロキシ / Webサーバー）**
  * クライアントからのリクエストを受信して Django アプリケーションコンテナへ転送。
  * 画像やスタイルシートなどの静的ファイルの配信レスポンスを行う。
* **App（アプリケーションコンテナ）**
  * **Django**: Nginx から受け取ったリクエストをもとに、ユーザー認証やHTMLの生成を行う。
  * **Django REST Framework (API)**: 授業やユーザーに紐づく情報の取得・更新、データ集計などの処理をAPIとして切り離し、DBを操作してレスポンスを返す。
  * **Signalling (Django Channels / WebSocket)**: WebRTC の P2P 通信確立に必要なシグナリング情報のリアルタイム仲介を担当。
* **DB（データベースコンテナ）**
  * PostgreSQL を稼働。Django REST Framework 等から受け取ったSQLをもとに、データの作成・取得・更新処理を実行。

## 🎯 課題とリファクタリング計画

開発を進める中で、コードの保守性やデータ整合性、ユーザー体験の観点から以下の課題を洗い出し、順次改善を進めています。

### 1. DB設計の見直し（ユーザーと授業の責務分離）
* **現状の課題**:
  * 授業時間などの本来授業側が保持すべきデータが、ユーザーオブジェクト側で管理されてしまっており、データモデルの責務分離が不十分。
* **改善アプローチ**:
  * 授業に関するデータ（授業時間数、ステータス等）を授業オブジェクトへ完全に分離・集約。
  * 授業データ単体で、ユーザーごとの総授業時間の集計や履歴管理を行える柔軟なデータ構造へ見直す。

### 2. ビジネスロジックの改善（状態管理と集計の健全化）
* **現状の課題**:
  * 授業接続が切れたタイミングのみで動的に時間を集計する仕様になっており、接続トラブル発生時の対応や事前キャンセル、日時変更といったイベント発生時の対応やステータスの追跡が複雑化しやすい。
* **改善アプローチ**:
  * 授業オブジェクト側で明確なステータス（`pending（未予約）`, `confirmed（予約済み）`, `completed（授業完了）`, `canceled（キャンセル済み）` 等）を定義して状態遷移を一元管理。
  * キャンセル処理や不具合時の巻き戻しといった各種イベントをシンプルにハンドリングできるようにし、ステータスが completed に確定した段階で該当授業時間分を冪等に集計するロジックに変更してシステムの安定性を高める。

### 3. WebRTC実装の検証と通信確立
* **現状の課題**:
  * ローカルでの自身の映像・音声表示までは実装できているが、不具合を解消できておらず相手との P2P 疎通（ビデオ通話）が完了していない。
* **改善アプローチ**:
  * フロントエンドとバックエンドの処理シーケンス（SDP/Offer/Answer/ICE candidate のやり取り）を根本から見直し。
  * STUN / TURN サーバーを用意し、ネットワーク境界を越えた疎通検証・接続エラーの解消を推進。

### 4. UI/UX およびコミュニケーション設計の向上
* **予約スケジュール表示の拡張**:
  * 当日の授業予定だけでなく、今後の予約一覧も確認・管理できるように改善。
* **講師選定体験の向上**:
  * 講師プロフィールにタグ機能や詳細な属性項目（指導スタイル・得意分野など）を追加し、生徒が自分に合った講師を見つけやすくする（将来的なタグベースのレコメンド機能への拡張も想定）。
* **明確な操作フィードバック**:
  * 「予約が完了しました」「プロフィールを変更しました」等の画面遷移や通知表示を統一し、ユーザーが迷わずに使える直感的なコミュニケーション設計を目指す。

### 5. AI・データ活用によるマッチング機能拡張
* **講師オンボーディング機能の追加**:
  * アカウント開設時に経歴・指導スタイル・性格・趣味などの詳細な項目を登録できるように設計。
  * 入力の手間を減らすため、キーワードや簡易情報をインプットするだけで、裏側でLLMのAPIと連携し、自然な自己紹介文や最適なタグを自動生成してDBに格納する支援機能の実装を検討。
* **データ基盤を活用したレコメンド・マッチングモデル**:
  * 生徒側と講師側の属性データ（学習目標、得意科目、性格、趣味など）をもとに、マッチ度を算出するロジック・モデルを裏側で構築。
  * 処理速度の速いデータ基盤を介して特徴量を高速処理し、生徒ごとに最もフィットする講師を自動でレコメンドできる設計を目指す。
